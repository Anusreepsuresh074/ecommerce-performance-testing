## Auth summary

| Journey step | Auth needed | How |
|---|---|---|
| `POST /auth/login` | No (this is where the token comes from) | Username + password in the JSON body |
| `GET /auth/me` | Yes, Bearer | `Authorization: Bearer <accessToken>` |
| `GET /products`, `/products/search`, `/products/{id}` | No | Public routes; no token is sent |

## Login request

```
POST /auth/login
Content-Type: application/json

{
  "username": "<from AUTH_USERNAME>",
  "password": "<from AUTH_PASSWORD>"
}
```

- `expiresInMins` is left out, so the token lasts the default 60 minutes (functional auth).
- **Success:** `200`, with body fields `id, username, email, firstName, lastName, gender, image, accessToken, refreshToken` (live check, matching functional auth). It also sets `Set-Cookie: accessToken` and `refreshToken`, both `HttpOnly; Secure` (live check).
- **Failure:** `400 "Invalid credentials"` or `400 "Username and password required"` (functional auth).

## Per-virtual-user token flow

| Part | Decision | Why |
|---|---|---|
| Source field | `$.accessToken` in the login response body | The Bearer value `/auth/me` needs (functional auth). `refreshToken` isn't needed (see Login frequency). |
| Extraction | **JSON Extractor** as a child of the login sampler. Variable `accessToken`, JSONPath `$.accessToken`, match no. `1`, default `NOT_FOUND`. | A detectable default, so a failed login can't silently send an empty token. |
| Isolation | Keep it a JMeter **variable** (per thread), never a property | Each virtual user holds its own token. A property is shared by every thread, so users would overwrite each other's tokens. |
| Sending | **HTTP Header Manager** as a child of the `/auth/me` sampler only: `Authorization` = `Bearer ${accessToken}` | Only that step needs it. A plan-wide header would send the token to public routes for no reason. |
| Login check | **Response Assertion** on the login sampler: code `200`; plus a **JSON Assertion** that `$.accessToken` exists | Failed logins show up as errors in the results. |
| Login failure | Thread Group *Action to be taken after a Sampler error* = **Start Next Thread Loop** | Without a token, `/auth/me` would fail too and double-count one problem; the next iteration logs in again. |
| Cookies | **No HTTP Cookie Manager** in the plan | Login sets an `accessToken` cookie and the API accepts it as auth (functional auth: `RULE-auth-cookie-token-accepted`). A Cookie Manager would send it automatically, so `/auth/me` could pass even with a broken Bearer header, and the test would no longer measure what it says it does. Nothing else in the journey needs cookies. |

## Login frequency

The token lasts **60 minutes**. The longest test in this project is PT-03 load at 11 minutes (plan caps: 15 minutes), so a token never expires mid-test and **refresh is never needed**.

Two options for `perf-test-design` to choose from:

| Option | What it means | Cost |
|---|---|---|
| **Log in every iteration** | Each loop of the journey is a new shopper session: login → me → browse → search → product | 5 requests per iteration, 1 of them a login. Realistic. |
| **Log in once per virtual user** (Once Only Controller around login) | Each user logs in on its first loop and reuses its token after | 4 requests per iteration after the first; more of the rate-limit budget goes to browsing |

**Recommendation:** log in **every iteration**. The journey is modelled as a shopper session, login is one of the steps whose speed matters, and the rate limit (`LIMIT-rate-100-per-10s`) is handled by keeping total throughput low, not by skipping logins. `perf-test-design` makes the final call.

## Credentials

- **Variables:** `AUTH_USERNAME`, `AUTH_PASSWORD`, the same names as the functional project (functional auth), so one `.env` shape works for both. The value is any public DummyJSON test user; all virtual users can share one (`context/perf-context.md`, Test-data facts). Names are listed in `.env.example` with empty values.
- **How they reach JMeter (verified locally):**
  1. `scripts/run-test.sh` exports `.env` as environment variables and never prints them.
  2. The Test Plan's **User Defined Variables** set `username` = `${__groovy(System.getenv('AUTH_USERNAME'))}` and `password` = `${__groovy(System.getenv('AUTH_PASSWORD'))}`. These are evaluated once at the start.
  3. The login body uses `${username}` and `${password}`.
- **Never** pass them with `-J`/`-G` (written to `jmeter.log`), put them in a CSV in `data/`, or type them into a `.jmx`.
- **CI:** GitHub repository secrets named `AUTH_USERNAME` and `AUTH_PASSWORD`, mapped to environment variables in the workflow step (`perf-ci-integration`). The ecommerce repo already uses these names.

## Results and log hygiene
- **No listener that saves response or request data** in committed plans: no View Results Tree, no Save Responses to a file. Login responses contain both tokens. JMeter's default CSV `.jtl` doesn't save bodies; keep it that way (`jmeter.save.saveservice.response_data` stays `false`).
- **No Debug Sampler or Debug PostProcessor** in committed plans; they print every variable, including `password` and `accessToken`.
- The HTML dashboard (`perf-report`) is built from the `.jtl`, which holds labels, timings and codes only, so it carries no secrets as long as the rules above hold.
- A token in a log is as good as a password until it expires (60 minutes by default).

### Not in scope
- `POST /products/add`, `PUT`/`PATCH`/`DELETE /products/{id}`: writes are simulated and nothing persists (functional context, `RULE-products-writes-simulated`), so they add load without modelling a real shopper's reads. Can be added later if the plan wants a write step.
- `POST /auth/refresh`: a default access token lasts 60 minutes, longer than any test here, so a journey never needs to refresh.
- `/auth/products…` (Bearer mirror): the same work as the public routes plus a token check; `/auth/me` already covers the authenticated path.
- Carts, users, posts, recipes and the other resources: out of scope, matching the functional project.

## User journeys
1. **Shopper journey:** `POST /auth/login` → `GET /auth/me` → `GET /products` (a page) → `GET /products/search?q=<term>` → `GET /products/{id}`. Data carried between steps: the `accessToken` from login is used for `/auth/me`; a product `id` can be taken from the search result to open that product.
2. **Anonymous browse (optional variant):** `GET /products` → `GET /products/categories` → `GET /products/category/{slug}` → `GET /products/{id}`. No login.

## Usage limits and constraints
- **LIMIT-rate-100-per-10s:** each client IP may make at most **100 requests per 10 seconds** (about 10 requests per second); above that the server answers with the message `"request limit exceeded, please wait a few seconds"` (repo: `src/middleware/rate-limiter.js`, `express-rate-limit` ^5.4.1, whose default status is `429`). **Confirmed live** on 2026-09-28: every response not served from the CDN cache carried `x-ratelimit-limit: 100` and an `x-ratelimit-reset` about 10 seconds ahead (observed). The limiter runs before every route (repo: `src/middleware/index.js`).
- **LIMIT-rate-shared-per-ip:** all JMeter virtual users run from one machine, so they **share one IP and one limit**. The limit caps total throughput for the whole test, not per user (repo + observed).
- **LIMIT-rate-counter-varies:** `x-ratelimit-remaining` jumped between 99, 98 and 50 on consecutive single requests (observed). This means either several server instances each counting separately, or other traffic from the same public IP (a shared office or carrier network). The safe reading is the strictest: 100 requests per 10 s in total, with some of that budget possibly used by others.
- **LIMIT-auth-token-lifetime:** access tokens last `expiresInMins` minutes, default 60, maximum 43200 (30 days) (docs, repo `src/constants/index.js`).
- **LIMIT-body-size-300kb:** request bodies are limited to 300 kB (repo: `src/middleware/index.js`). Not relevant to a read-only journey.
- **LIMIT-delay-param-0-5000:** the `delay` param adds 0–5000 ms of artificial latency (docs). It must not be sent in performance tests, because it would fake the measurement.
- **Fair-use policy / terms of service:** not stated in the docs (docs).

## Environment traits
- **Public, shared, free service** run by one maintainer (docs, repo). Load from this project competes with every other DummyJSON user.
- **Behind Cloudflare** (`server: cloudflare`, `cf-ray` headers; observed). Every request goes over the public internet, so results include internet latency from the test machine's network.
- **CDN cache serves some URLs:** `GET /products` (no query) and `GET /products/1` came back `cf-cache-status: HIT` with `age` of about 4.7 days, and those cached copies even carry stale rate-limit headers, so they never reach the server (observed). `/products?limit=…&skip=…`, `/products/search`, `/products/categories`, `/products/7`, `/auth/login` and `/auth/me` came back `DYNAMIC`, meaning they reach the server (observed). Which ids are cached isn't predictable.
- **Data is in memory:** products and users are read from a frozen in-memory data set, not a database (repo: `src/controllers/auth.js` `frozenData.users`). The server's own work per request is small; most of the measured time is network.
- **Responses are gzip-compressed** (repo: `compression` middleware). The server's `node-cache` middleware exists but is not applied to the product or auth routes (repo: `src/routes/product.js`, `src/routes/auth.js`).

## Risks for performance testing
- **The rate limit is lower than a "real" load test would need.** At about 10 requests per second in total, a stress test that "adds users until it breaks" would break on the rate limiter (`429`), not on server capacity. The plan must keep throughput well under the limit, and treat any `429` as "our test was too heavy", not as an API defect.
- **One IP, possibly shared.** Other traffic from the same network could use part of the budget, so the plan needs a safety margin under 100 per 10 s.
- **Cached URLs measure Cloudflare, not the API.** The plan should use URLs that reach the server (query parameters, varied ids and search terms) and record the `cf-cache-status` split.
- **The baseline is already slow for one user** (median about 0.6–0.85 s, max 1.4 s, mostly network). A threshold like "p90 under 1 s" could fail with no load at all. Thresholds should be set relative to the measured single-user baseline, not to a generic number.
- **Results depend on the test machine's network** and differ between a laptop and a GitHub Actions runner. Compare runs from the same place.
- **Free public service etiquette:** runs must be short and small, even when the limit would allow more.

## Open questions / follow-ups
- **No SLA exists.** A human must approve the assumed thresholds in the test plan.
- **Is the network IP shared?** `x-ratelimit-remaining: 50` on one request suggests other traffic on the same IP, or a different server instance. It's worth re-checking on the day of a run; if it's shared, lower the caps further.
- **Instance count is unknown.** If several server instances each keep their own counter, the real limit is higher than 100 per 10 s, but that can't be relied on, so the plan uses the strict reading.
- **GitHub Actions runners use different IPs** (shared among many GitHub users), so CI runs may hit the limit sooner or differently. `perf-ci-integration` should keep CI to the smallest profile.

_Follow-up after execution (2026-09-28, `docs/test-summary-report.md`): during the runs, the lowest `x-ratelimit-remaining` was 71 while our own traffic used about 12–13 per 10 s, which confirms other traffic shares the budget. The plan's caps held, with no `429` in 3,523 samples. CI runs smoke on every push and load only by hand; baseline, stress and spike are local only._
